# NEXUS-7 Closed-Loop Product Plan

> 状态：v2.0 本地/reference 实现闭环；外部生产证据待完成
> 规划范围：v1.4.0 → v2.0.0
> 更新日期：2026-07-18
> 当前基线：v2.0.0 Closed-Loop Autonomy Lab

## 1. 结论

NEXUS-7 不应继续横向增加彼此孤立的赛博朋克面板。它应收敛为：

> **一个以合成城市为可重复环境、以多智能体为干预者、以人类为最终治理者的可验证自主系统实验室。**

城市是实验载体，不是装饰；Agent 是受约束的提案者和执行者，不是权威；
模型输出是待验证证据，不是真相；“自我迭代”是经过实验、审批、发布、
监控和回滚的工程流程，不是进程任意修改自己的代码。

本计划以 v2.0 为闭环终点。达到 v2.0 后，系统必须能够把一次城市问题完整地
走完：

```text
发现 → 定义影响 → 诊断 → 提出干预 → 反事实实验 → 风险审批
  → 分阶段执行 → 持续观测 → 独立归因 → 保留或回滚
  → 沉淀经验 → 触发下一轮受治理改进
```

如果其中任意一段只能靠硬编码演示、人工补写证据或不可重放的模型回答完成，
就不算闭环。

## 2. 产品意义

### 2.1 对人类有什么意义

NEXUS-7 最有价值的方向不是“展示一个 AI 管理城市”，而是成为自主决策系统的
风洞和显微镜：

- 在无真实社会代价的合成环境里反复制造冲击、冲突和失败；
- 观察多个 Agent 如何争夺资源、权衡目标并暴露协作缺陷；
- 区分“系统做了动作”与“动作确实带来可归因的公共收益”；
- 检验审批、最小权限、证据时效、灰度和回滚是否真的有效；
- 让研究者、开发者和普通观察者都能追问“为什么、凭什么、结果如何”；
- 为现实中的自主系统积累可迁移的验证方法，而不是宣称模拟等于现实。

### 2.2 人类应当观察什么

系统不应暴露或伪造模型的隐藏思维链。它应公开可审计的决策记录：

- 当时看到了什么事实；
- 哪些事实不确定或缺失；
- 提出了哪些候选方案；
- 哪些方案被拒绝，以及依据是什么；
- 采用方案的预期收益、风险和保护指标；
- 实验与真实执行后的差异；
- 谁授权了执行；
- 最终产生了什么结果；
- 系统从结果中形成了哪条可检验经验。

## 3. 北极星与防投机指标

### 3.1 新北极星：Verified Beneficial Closure Rate

**可验证有益闭环率（VBCR）**：

```text
在规定时间内完成全链路、独立验证为有益且无保护指标越界的问题数
----------------------------------------------------------------
所有符合处理条件的问题数
```

一个问题只有同时满足以下条件，才进入分子：

1. 检测证据和影响范围完整；
2. 诊断包含候选原因、反证和置信度；
3. 干预经过同基线反事实实验；
4. 风险、权限、审批和发布策略全部通过；
5. 执行后在预定观测窗口内优于冻结基线；
6. 所有保护指标保持在政策阈值内；
7. 因果链、重放坐标、版本和回滚信息完整；
8. 结果由独立 evaluator 判定，不由提案 Agent 自评；
9. 经验已沉淀，或明确标记为“不足以学习”；
10. 问题被正式关闭，且仍可被新证据重新打开。

### 3.2 v2.0 目标

| 指标 | v2.0 退出阈值 |
|---|---:|
| 可验证有益闭环率 | ≥ 80% |
| 符合条件问题检测覆盖率 | ≥ 95% |
| 严重保护指标逃逸 | 0 |
| 已接受动作因果链完整度 | 100% |
| 确定性重放成功率 | ≥ 99.9% |
| 注入故障自动回滚覆盖率 | 100% |
| 关闭问题的结果评估覆盖率 | 100% |
| 生产级动作有效签名策略覆盖率 | 100% |
| 过期关键证据绕过次数 | 0 |
| 公共场景可复现实验通过率 | 100% |

VBCR 不能单独使用，否则系统可能通过不处理困难问题来提高分数。因此必须同时
展示检测覆盖率、未决问题年龄、回滚率、严重逃逸数、人类否决率和各利益相关群体
的影响分布。

## 4. 闭环模型

### 4.1 七个必须同时闭合的环

| 闭环 | 输入 | 输出 | 当前状态 |
|---|---|---|---|
| 世界状态环 | 场景、事件、动作 | 确定性世界与指标 | 本地闭合 |
| Agent 行动环 | 观测、能力、预算 | 提案、命令、评估 | 本地闭合 |
| 实验环 | 假设、候选干预 | 基线/候选因果证据 | 本地闭合 |
| 运营环 | 已批准制品 | 灰度、SLO、回滚证据 | 本地闭合；真实 controller 证据待外部 |
| 治理环 | 身份、策略、证据 | 授权、审计、追责 | 本地闭合；远端身份/签名证据待外部 |
| 学习环 | 长期结果 | 经验、策略改进提案 | 本地闭合 |
| 人类价值环 | 目标、反馈、异议 | 权衡、申诉、公共解释 | 本地闭合 |

只有七个环全部具备持久状态、可重放事件和失败路径，产品才算闭环。

### 4.2 问题生命周期

所有跨模块改进统一使用一个持久状态机：

```text
detected
  → triaged
  → diagnosing
  → diagnosed
  → planned
  → experimenting
  → awaiting-approval
  → staged
  → monitoring
  → verified-beneficial | rolled-back | inconclusive
  → learned
  → closed
```

附加转换：

- 任意非终态可进入 `paused`、`blocked` 或 `cancelled`；
- 新证据可以把 `closed` 重新打开为 `detected`；
- 保护指标越界必须直接进入 `rolled-back`，不能等待模型决定；
- `inconclusive` 不能被包装成成功，只能补充实验或安全关闭；
- `learned` 只产生新的候选策略/测试/文档，不直接修改生产策略。

### 4.3 最小领域对象

| 对象 | 作用 | 必须包含 |
|---|---|---|
| Objective | 人类定义的目标 | owner、指标、方向、期限、权重 |
| Guardrail | 不得牺牲的边界 | 阈值、适用群体、严重度、动作 |
| Incident | 需要处理的问题 | 证据、影响、状态、SLO、负责人 |
| Hypothesis | 对原因的可证伪解释 | 支持证据、反证、置信度、替代解释 |
| Intervention | 可执行候选方案 | 前置条件、预期效果、成本、逆操作 |
| Experiment | 冻结的比较设计 | 基线、候选、样本、停止规则、版本 |
| Decision | 权衡与授权 | 候选集、拒绝原因、审批、策略 |
| Deployment | 分阶段执行 | 制品、环境、流量、遥测、回滚 |
| Outcome | 独立结果判断 | 观测窗口、效应量、保护指标、结论 |
| Lesson | 可复用经验 | 适用条件、失效条件、来源、状态 |
| Feedback | 人类反馈与异议 | 提交者范围、对象、处理、申诉结果 |

这些对象必须通过稳定 ID、`correlationId`、`causationId` 和证据摘要连接，
不能依赖 UI 文案推断关系。

## 5. 版本路线

版本顺序是依赖顺序，不是日历承诺。每个版本都必须完成数据模型、服务、API、
界面、双语、迁移、测试、文档和证据，不能只完成 UI。

## v1.4.0 — Operational Intelligence | 运营智能

### 目标

让系统不只显示“当前是否健康”，还可以回答“何时开始变差、是否持续、谁收到
告警、如何升级、谁临时取得了权限”。

### P0 特性

1. **统一 SLO 时序仓库**
   - 持久化 model、deployment、recovery、worker、evidence、policy SLO 样本；
   - 每个样本带 workspace、environment、artifact、policy 和 trace 维度；
   - 支持原始、小时、日聚合及可配置保留周期；
   - PostgreSQL 与 memory adapter 共享查询合约。

2. **Alert 与 Incident 基础域**
   - 规则、触发、去重、抑制、确认、解决和重新打开；
   - 关联原始 SLO 样本和受影响资源；
   - 稳定告警代码，不把自由文本作为机器接口；
   - 告警风暴预算和相同根因聚合。

3. **外部通知与升级**
   - 通用 signed webhook adapter；
   - delivery attempt、重试、退避、死信和回执；
   - freshness、policy expiry、rollback、worker lease、RPO/RTO 规则；
   - 通知目标按组织、环境、严重度配置；
   - 测试通道和 dry-run，不把真实 secret 写入前端或审计详情。

4. **访问治理**
   - 组织级委派管理员与职责分离；
   - 定期 access review campaign、证明和撤权；
   - 双人 break-glass、短 TTL、用途声明、自动回收和事后复核；
   - orphaned service account 与过期凭据报告。

5. **部署控制器合规套件**
   - 版本化 HTTP contract；
   - reference fake controller 与故障注入 fixture；
   - timeout、重复请求、乱序遥测、部分失败、回滚幂等测试；
   - conformance report 作为部署 adapter 的准入证据。

6. **Operations Center**
   - SLO 趋势、告警队列、证据年龄、策略到期、访问复核和演练历史；
   - 可按组织、工作区、环境、版本、时间过滤；
   - 从图表下钻到原始证据和审计记录；
   - 桌面、移动端、键盘和屏幕阅读器可用。

### P1 特性

- 维护窗口与告警抑制；
- 通知值班表导入；
- SLO burn-rate 多窗口告警；
- 治理报表的 JSON/CSV 导出。

### 退出门禁

- 至少 30 天合成时序可聚合且原始样本可追溯；
- 相同告警重复投递不会创建多个 incident；
- 通知失败可重试并最终进入可见死信；
- break-glass 到期自动撤权，完整记录两位批准者；
- controller conformance 覆盖成功、超时、重试、故障和回滚；
- 旧 v1.0-v1.3 API、证据和备份继续兼容。

## v1.5.0 — Coherent City & Incident Model | 一致城市与事件模型

### 目标

让城市真正成为一个可推理系统，而不是共享几个数字的面板集合。

### P0 特性

1. **城市 ontology**
   - 人口、区域、住房、交通、能源、经济、公共安全、环境和数字网络；
   - 明确实体关系、单位、合法范围、更新频率和责任 Agent；
   - 指标字典记录来源、计算式、可观测性和敏感性。

2. **跨域机制**
   - 能源短缺影响交通与生产；
   - 拥堵影响生产率、污染与幸福度；
   - 住房成本、就业和公共服务影响迁移与不平等；
   - 数字网络故障影响经济和应急响应；
   - 所有影响通过领域事件发生，不允许组件自行随机改值。

3. **Incident 真值与影响范围**
   - 场景可声明隐藏根因、可观测症状和受影响群体；
   - 同一异常可聚合为一个跨域 incident；
   - severity 同时考虑规模、持续时间、脆弱群体和不可逆性；
   - 支持误报、漏报和延迟检测评估。

4. **目标与保护指标注册表**
   - 城市级、组织级、场景级目标；
   - 多目标权重、硬约束和冲突声明；
   - 公共安全、基本服务、公平性和预算作为默认保护维度；
   - 目标版本冻结到每次实验和决策。

5. **遗留视图收敛**
   - Weather、Resource、Trading、Emergency、Analytics、News 全部读取统一事件；
   - 成就、任务、ARIA 和 Evolution Log 引用真实领域对象；
   - Hacker、Satellite、Quantum 等叙事模块要么接入世界机制，要么明确标记为
     sandbox，不再制造貌似生产的指标。

### 场景扩展

至少覆盖五类事件族：

- 基础设施级联故障；
- 经济冲击与资源短缺；
- 公共安全与应急响应；
- 环境污染与极端天气；
- 数字网络攻击或服务中断。

每类至少包含正常、单点故障、级联故障和相互冲突目标四种场景。

### 退出门禁

- 所有主视图的核心指标都能追溯到同一个世界快照或事件；
- 20 个以上公共场景可确定性重放；
- 所有指标具有单位、来源、范围和 owner；
- 场景真值可以计算检测 recall、precision 和 detection delay；
- 不存在未声明的 `Math.random()`、组件私有时钟或独立业务状态。

## v1.6.0 — Causal Diagnosis | 因果诊断

### 目标

从“阈值触发动作”升级为“系统能提出可证伪原因，并知道自己可能错了”。

### P0 特性

1. **Hypothesis Graph**
   - 症状、候选根因、中间机制、支持证据和反证；
   - 每条边记录来源、时间范围、置信度和适用场景；
   - 保留被拒绝假设，禁止事后只展示胜者。

2. **诊断 Agent 协议**
   - 各领域 Agent 独立提出和反驳假设；
   - ARIA 只聚合冲突，不可覆盖来源；
   - 模型生成假设必须映射到已知实体、事件和可执行检验；
   - 缺证据时输出 `unknown` 或 `inconclusive`。

3. **反事实诊断**
   - 从 incident 前快照建立冻结基线；
   - 单独移除或改变候选原因；
   - 对比症状是否消失及其他指标变化；
   - 记录 effect size、置信区间和替代解释。

4. **漂移与校准**
   - 记录预测概率与实际结果；
   - 按 Agent、模型、事件族和环境展示校准；
   - 检测数据分布、政策效果和模型输出漂移；
   - 漂移越界后降级为 deterministic policy 或只读建议。

5. **Causal Explorer**
   - incident 时间线、假设图、证据强弱、反事实对比；
   - 明确区分事实、推断、预测和人类判断；
   - 展示“我们不知道什么”和“什么证据会改变结论”；
   - 提供面向普通观察者和审计人员的两种解释密度。

### 退出门禁

- 公共场景的隐藏根因 Top-3 命中率达到既定基线；
- 每个已诊断 incident 至少包含一个替代假设和一条反证；
- 所有因果结论都能从冻结快照重跑；
- 低置信度诊断不会进入自动实验；
- 诊断界面不展示或声称暴露模型隐藏思维链。

## v1.7.0 — Goal-Constrained Planning | 目标约束规划

### 目标

把已诊断问题转化为多方案、可比较、有预算、有停止条件的干预实验。

### P0 特性

1. **Intervention DSL**
   - 只允许声明式、能力受限、可逆或显式不可逆的干预；
   - 每个动作声明成本、资源、预计延迟、适用条件和 inverse；
   - 禁止模型提交任意代码、shell 或数据库语句。

2. **候选方案组合**
   - 规则 Agent、模型 Agent 和人类都可提出候选；
   - 去重等价方案，保留来源与差异；
   - 显示不行动基线；
   - 对公共收益、成本、风险和群体影响做 Pareto 比较。

3. **实验设计器**
   - 自动生成同种子 baseline/candidate；
   - 冻结目标、保护指标、样本量、观察窗口和停止规则；
   - 支持多种子重复、顺序检验和提前停止；
   - 对多重比较、回归均值和自然周期作显式防护。

4. **实验组合调度**
   - 按风险、预期信息增益、资源预算和 incident 严重度排序；
   - 防止同一世界中的干预互相污染；
   - 对互斥资源和并发实验做冲突解析；
   - 记录未执行实验及排队原因。

5. **决策评审**
   - 并列展示所有候选及其拒绝原因；
   - 人类可以批准、修改、要求补证据或否决；
   - 高风险/不可逆干预强制双人审批；
   - 决策冻结目标、证据、策略和制品版本。

### 退出门禁

- 每个计划至少比较“不行动”和两个有效候选，除非记录例外；
- 同一实验设计可以在 memory 和 PostgreSQL backend 得到一致结果；
- 保护指标越界在首次采样后自动停止；
- 预算、能力或审批缺失时无法进入 staged；
- 决策记录可以解释为何选择当前方案及为何拒绝其他方案。

## v1.8.0 — Outcome Learning | 结果学习

### 目标

让系统依据延迟结果更新“可检验的组织记忆”，而不是依据模型自我评价更新自己。

### P0 特性

1. **Outcome Evaluator**
   - 与提案 Agent 隔离的评估器；
   - 支持短、中、长三个观测窗口；
   - 与冻结反事实、历史基线和季节性对比；
   - 输出 beneficial、harmful、neutral 或 inconclusive；
   - 迟到事件会重新计算并可能 reopen incident。

2. **Lesson Registry**
   - 经验包含适用条件、失效条件、效应量、置信度和证据来源；
   - success、failure、rollback 和 inconclusive 同等保留；
   - 经验有 draft、validated、deprecated、invalidated 生命周期；
   - 不允许无来源的“最佳实践”进入策略。

3. **Playbook**
   - 把已验证经验组合成可读、可测试的响应剧本；
   - 运行前重新检查上下文是否满足；
   - 剧本执行仍经过能力、预算、实验和审批；
   - 发现漂移时自动降低可信级别。

4. **受治理策略改进**
   - 经验只能生成 policy/prompt/scenario/test 提案；
   - 每个提案必须说明训练/检索证据和预期影响；
   - 经过回归语料、公共场景、隔离执行和发布链；
   - 旧版本可重放、可回滚、可废止。

5. **Learning Observatory**
   - 展示系统学到了什么、从哪次结果学到、在哪些条件下失效；
   - 显示长期效果与最初预测之间的误差；
   - 显示经常被遗忘、反复失败或互相矛盾的经验；
   - 允许人类标记错误归因并触发复核。

### 退出门禁

- 每个 closed incident 都有 outcome 和 lesson disposition；
- harmful/rollback 结果不会被检索为正向推荐；
- 经验撤销会使引用它的 playbook 和策略重新评估；
- 任何自动生成的改进仍需通过现有发布治理；
- 同一历史数据重建后得到相同的 lesson 状态。

## v1.9.0 — Participatory Governance | 参与式治理

### 目标

把“人类审批”从一个管理员按钮扩展为目标制定、影响审查、反馈、异议和申诉。

### P0 特性

1. **Stakeholder 与影响视图**
   - 合成居民群体只表示场景角色，不冒充现实人口；
   - 结果按区域、收入、服务可达性和脆弱度分解；
   - 平均指标改善但特定群体严重受损时不能判定为有益；
   - 群体定义、权重和保护政策全部版本化。

2. **Goal Deliberation**
   - 人类提出、讨论、修改和批准目标；
   - 记录冲突目标和少数意见；
   - 在执行前模拟政策对不同群体的影响；
   - 目标不能由 Agent 在无授权时自行提高权重。

3. **反馈、异议与申诉**
   - 反馈可关联 incident、decision、deployment、outcome 或 lesson；
   - 支持纠错、反对、补充证据和申诉；
   - 有 SLA、负责人、状态和最终答复；
   - 成功申诉可 reopen incident 或 invalidate lesson。

4. **公共解释**
   - 每次重要决策生成事实、方案、权衡、授权、结果的可读摘要；
   - 同时提供机器可读 evidence bundle；
   - 对不确定性和模拟边界使用明确语言；
   - 中英文一致且通过无障碍测试。

5. **治理模拟与红队**
   - 测试审批串谋、权限升级、证据伪造、目标投机和告警压制；
   - 定期演练 emergency stop、break-glass 和申诉；
   - 对 Goodhart、automation bias 和 minority harm 建立固定场景；
   - 红队结果进入 release gate。

### 退出门禁

- 每个高影响决策都有目标 owner、影响分解和人类授权；
- 严重群体伤害即使平均值改善也会阻止晋级；
- 反馈和申诉可以改变决策状态并留下不可变审计；
- 公共解释能从结构化事实重建，不依赖模型自由发挥；
- 治理攻击场景全部被阻止、检测或安全回滚。

## v2.0.0 — Closed-Loop Autonomy Lab | 闭环自主实验室

> 实现状态：P0 代码、固定 corpus、memory/PostgreSQL、API、双语 UI、
> 迁移/备份、故障路径、机器认证与文档已完成；当前工作树无远端 attestation，
> 因而状态为 `implementation complete / external evidence pending`。

### 目标

将前述能力集成为一个可公开验证、可扩展、可运营的完整产品，而不是新增新的
业务域。

### P0 特性

1. **Closed-Loop Orchestrator**
   - 实现统一问题状态机和超时/补偿逻辑；
   - 每一步有 owner、deadline、前置证据和允许转换；
   - 幂等恢复进程中断，保证不会重复执行外部动作；
   - 支持人工 pause、resume、cancel、rollback 和 emergency stop。

2. **端到端演练库**
   - 20+ 公共场景、5 类事件族、正常与恶意输入；
   - 覆盖成功、回滚、无解、错诊、迟到伤害、审批否决和证据过期；
   - 每个场景声明真值、目标、保护指标和预期安全行为；
   - 固定 release corpus，新增场景不能偷偷改变旧阈值。

3. **v2 Verification Contract**
   - 发布 VBCR、检测覆盖、诊断质量、实验完整度、保护指标、结果评估、
     学习处置、治理覆盖和运营恢复；
   - 报告可机器读取、带 schema version 和 canonical fingerprint；
   - 将 public suite、PostgreSQL、浏览器、live provider、deployment、
     recovery 和 governance red-team 证据绑定到同一 release artifact；
   - 本地证据和外部可信证据继续明确区分。

4. **扩展认证**
   - Agent、model provider、scenario、repository、notification、
     deployment controller、outcome evaluator 均有版本化 contract；
   - 提供 reference implementation 和 conformance tests；
   - 扩展声明能力、数据访问、网络需求和失败模式；
   - 未认证扩展只能运行在 sandbox workspace。

5. **Observer 统一入口**
   - 从城市地图进入 incident，再进入假设、实验、决策、部署、结果和经验；
   - 任意图表点都能下钻到来源事件；
   - 任意动作都能找到触发原因和 inverse；
   - 普通观察者、operator、auditor 看到适合各自角色的信息密度。

6. **运营就绪**
   - 完整迁移、备份、恢复、数据保留和 schema compatibility；
   - 多租户隔离、速率限制、并发和故障恢复压测；
   - SLO、值班手册、故障手册、安全威胁模型和数据分类；
   - 安装、升级、回滚和灾难恢复都有自动化演练证据。

### v2.0 闭环认证场景

至少有一个完整演示必须在不手工补数据的情况下完成：

1. 场景注入跨域级联故障；
2. 系统检测并形成一个 incident；
3. 多 Agent 提出冲突假设；
4. 反事实实验排除错误原因；
5. 规划器产生至少两个干预和不行动基线；
6. 人类审批符合策略的候选；
7. 同一制品依次进入 development、staging、production；
8. 监控发现短期改善；
9. 延迟观测发现或排除长期副作用；
10. evaluator 给出有益、回滚或不确定结论；
11. lesson registry 更新并生成下一轮提案；
12. 新提案再次经过原有验证与治理链；
13. Observer 可以从最终结论回溯到第一条观测；
14. 重放得到相同世界状态、决策记录和学习处置。

### v2.0 停止条件

以下条件全部满足后，核心产品闭环完成：

- 七个闭环都有持久对象、事件、失败路径和 UI；
- 上述 v2.0 指标达到阈值；
- 所有高风险动作都可暂停、审批、回滚和追责；
- 系统能够诚实输出“不知道”“不行动”和“实验无结论”；
- 学习结果不能绕过发布治理；
- 合成结果不被描述为现实政策效果；
- 新扩展不需要修改闭环核心即可接入；
- 删除任何一个闭环阶段都会导致 verification 明确失败。

达到这些条件后，优先进入稳定维护和外部复现，而不是立即继续增加版本号。

本地/reference 退出结果（2026-07-18）：

| 指标 | 结果 |
|---|---:|
| VBCR | 80%（16/20 eligible） |
| 检测覆盖 | 100% |
| 确定性重放 | 100% |
| 已接受动作因果链 | 100% |
| 注入故障回滚 | 100% |
| 关闭处置、证据完整、固定 corpus | 100% |
| 严重保护指标逃逸 / 过期证据绕过 | 0 / 0 |
| 认证场景 / 扩展边界 | 25 / 7 |

完整口径见 `docs/V2_VERIFICATION.md`；统一状态机和恢复路径见
`docs/CLOSED_LOOP_ORCHESTRATION.md`。这些结果不替代 live model、真实
deployment controller、真实恢复演练和远端 Sigstore receipt。

## 6. 跨版本工程计划

### 6.1 固定工作流

每个特性必须以垂直切片交付：

1. 定义领域对象、状态机和不变量；
2. 定义 repository interface 和 memory reference adapter；
3. 添加 PostgreSQL migration 与向后兼容；
4. 实现 service，不把业务规则写进 React 或 route；
5. 添加最小权限和 workspace 隔离；
6. 实现 JSON API/SSE 或查询接口；
7. 实现中英文 UI 与机器可读导出；
8. 添加 unit、property、integration、browser、accessibility 测试；
9. 增加故障注入、回滚和恢复用例；
10. 更新 ADR、operations guide、AGENTS 和 iteration manifest；
11. 生成本地 evidence；外部发布再绑定远端 attestation；
12. 验证旧 schema、旧备份、旧报告和旧公共场景。

### 6.2 建议模块边界

```text
src/
├── objectives/       目标、保护指标与利益相关者
├── incidents/        告警聚合、状态机与影响范围
├── diagnosis/        假设图、反证、反事实与校准
├── interventions/    声明式干预与能力合约
├── experiments/      运行、快照、分支与比较
├── outcomes/         独立结果评估与延迟窗口
├── learning/         lesson、playbook 与改进提案
├── governance/       身份、审批、策略、反馈与申诉
├── operations/       SLO、通知、演练、备份与恢复
└── verification/     v1/v2 兼容报告与公共场景
```

模块可以渐进形成，不要求一次重构。领域对象应先通过 service interface 隔离，
再移动目录，避免“大爆炸式”重写。

### 6.3 数据与兼容策略

- 事件 append-only；修正使用新事件，不回写历史；
- 重要读模型可以重建，并记录构建版本；
- 每个 schema 有版本和迁移器；
- v1 报告在 v2 继续可读取，v2 使用新 endpoint 或显式 schema negotiation；
- 备份升级时至少支持上一个 minor release 的直接恢复；
- 大表采用 retention、partition 或聚合前先用真实基准证明需要；
- 不把模型 prompt、PII、token 或 secret 写入领域事件；
- 所有外部输入记录摘要、来源和验证结果。

### 6.4 测试矩阵

| 层 | 必测内容 |
|---|---|
| 领域单元 | 状态转换、不变量、预算、能力、幂等 |
| 属性测试 | 任意事件序列不越界、重放一致、inverse 可恢复 |
| 场景回归 | 真值检测、诊断、计划、结果和学习 |
| PostgreSQL | 事务、并发、迁移、备份、恢复、读模型重建 |
| Contract | OIDC、webhook、deployment、provider、extension |
| 安全 | 越权、重放攻击、伪造签名、SSRF、secret 泄漏 |
| 浏览器 | 完整闭环、移动端、键盘、WCAG A/AA |
| Chaos | worker 丢失、DB 重启、通知失败、遥测乱序、外部超时 |
| 长周期 | 指标有界、队列不泄漏、状态最终收敛 |
| 外部证据 | live model、真实 controller、recovery、attestation |

### 6.5 发布节奏

每个版本使用四个内部门：

- **Contract freeze**：对象、事件、权限和兼容规则确定；
- **Vertical slice**：至少一个场景贯穿数据、服务、API、UI；
- **Failure complete**：超时、拒绝、回滚、恢复和不确定路径完成；
- **Evidence complete**：本地全门禁与所需外部证据完成。

只有最后一个门通过才标记版本完成。没有外部环境时，必须写成
“implementation complete / external evidence pending”，不能用本地 mock 替代。

## 7. 优先级与明确不做

### 7.1 闭环前不优先

- 新增彼此独立的赛博朋克面板；
- 纯视觉 3D 城市扩建；
- 与闭环无关的小游戏、交易品种或成就；
- 未接入领域事件的实时新闻和天气内容；
- 多人社交、排行榜、代币或商业市场；
- 无 evidence contract 的第三方插件市场；
- 为了“更像 AI”而增加不可复现的自由对话。

这些功能可以保留现状，但新增投入必须证明它提高观测、诊断、实验、治理或
学习中的至少一个闭环指标。

### 7.2 永久非目标

- 控制真实城市基础设施；
- 宣称模拟居民代表真实人群；
- 无人类授权的高风险生产部署；
- 让模型直接执行 shell、写数据库或修改生产策略；
- 保存或展示隐藏思维链；
- 用单一幸福度、GDP 或 Agent 活跃度代表公共价值；
- 将 VBCR 包装成通用智能或现实治理能力证明。

## 8. 风险与约束

| 风险 | 可能表现 | 设计约束 |
|---|---|---|
| Goodhart | 为提高闭环率忽略难题 | 同时约束覆盖率、年龄、逃逸和群体影响 |
| 错误因果 | 相关性被当成干预效果 | 冻结基线、反事实、替代假设、独立 evaluator |
| 自动化偏见 | 人类只点击批准 | 展示候选差异、反证、否决和随机审计 |
| 告警疲劳 | 大量重复通知 | incident 聚合、预算、抑制、升级和回执 |
| 权限膨胀 | service account 长期高权 | 固定模板、TTL、review、双人 break-glass |
| 学习污染 | 一次偶然成功变成规则 | lesson 生命周期、适用条件、重复验证 |
| 模拟越界 | 把合成结论用于现实政策 | UI、导出和文档强制 synthetic 标签 |
| 数据泄漏 | prompt、token 或反馈含敏感数据 | 分类、最小化、摘要、脱敏、保留策略 |
| 供应链风险 | 扩展或制品被替换 | exact artifact、attestation、contract certification |
| 无限迭代 | 永远新增功能但无终态 | v2.0 停止条件和版本退出门禁 |

## 9. 历史第一执行队列：v1.4

   `NotificationDelivery` 合约；

8. 实现组织委派、access review 和双人 break-glass；
9. 发布 deployment-controller contract v1 与 conformance fixtures；

## 10. 规划完成的判据

这份规划本身在以下条件下视为闭合：

- 每个缺失闭环都有对应版本；
- 每个版本都有 P0 特性和机器可判定退出门禁；
- v2.0 有明确终态和停止条件；
- 当前 v1.3 能力被复用而不是推倒重来；
- 高风险外部依赖有 mock contract 和真实 evidence 的明确边界；
- 产品意义、非目标、风险和优先级都被写明；
- 第一执行队列可以直接转为 issue 或开发任务。

后续修改本计划时，应保留旧目标的变更理由，避免路线图随实现便利性静默漂移。
